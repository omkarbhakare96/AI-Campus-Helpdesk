# AI-Based Campus Helpdesk
### Intelligent Complaint Classification, Priority Prediction and Resolution Tracking System

A full-stack, AI-powered mini-project that lets students submit campus complaints and
automatically classifies them, predicts priority, detects sentiment, flags duplicates,
routes them to the correct department, and lets both students and admins track
resolution end-to-end.

---

## 1. Problem Statement

Colleges receive a large volume of complaints and service requests every day — network
outages, hostel issues, lab equipment failures, exam grievances, and more. Manually
reading, classifying, prioritizing, and routing each complaint to the right department
is slow, inconsistent, and error-prone. Urgent issues (a safety hazard, a fire risk) can
get buried under a queue of low-priority complaints that arrived first. There is also no
easy way to detect that ten students have already reported the exact same issue.

## 2. Aim and Objectives

**Aim:** To design and implement an AI-powered web application that automates the
triage of campus complaints using Natural Language Processing and Machine Learning.

**Objectives:**
1. Build a system where students can submit complaints in free-text form.
2. Use NLP + ML to automatically classify complaints into departments.
3. Predict the urgency (priority) of each complaint from its text.
4. Detect the emotional tone (sentiment) of each complaint.
5. Detect duplicate/similar complaints using text similarity.
6. Provide a ticketing system for tracking complaint status.
7. Provide an admin dashboard for management, filtering and analytics.
8. Ensure the system is secure (hashed passwords, input validation, role-based access).

## 3. Methodology

1. **Data collection** — a labeled dataset of 300+ realistic college complaints was
   synthetically generated (`generate_dataset.py`) covering 12 categories, 4 priority
   levels, and 3 sentiment classes.
2. **Preprocessing** — lowercasing, URL removal, punctuation/special-character removal,
   whitespace normalization (`clean_text` in `train_model.py` / `app/ai/inference.py`).
3. **Feature extraction** — TF-IDF vectorization (unigrams + bigrams, 3000 features).
4. **Model training** — three independent Logistic Regression classifiers are trained
   on the same TF-IDF features: one each for category, priority, and sentiment.
5. **Evaluation** — Accuracy, Precision, Recall, F1-score and Confusion Matrix are
   computed on a held-out 20% test split for every model.
6. **Duplicate detection** — at inference time, the new complaint's TF-IDF vector is
   compared against every existing complaint in the database using cosine similarity;
   a match above 0.72 is flagged as a probable duplicate.
7. **Serving** — the trained models are saved as `.pkl` files with `joblib` and loaded
   once by the FastAPI backend to serve real-time predictions.
8. **Full-stack integration** — FastAPI (backend + REST API) + Jinja2/HTML/CSS/JS
   (frontend) + SQLite/SQLAlchemy (database) are wired together into one runnable app.

## 4. Dataset Description

File: `dataset/complaints.csv` (generated by `generate_dataset.py`)

| Column | Description |
|---|---|
| `complaint_text` | Free-text complaint, written in varied realistic phrasing |
| `category` | One of 12 departments (IT/Network, Infrastructure, Laboratory, Library, Hostel, Transport, Electricity, Cleanliness, Examination, Administration, Security, Other) |
| `priority` | Low / Medium / High / Critical |
| `sentiment` | Positive / Neutral / Negative |

The dataset contains **360 records** (30 per category), built from realistic templates
combining subjects (e.g. "the hostel water supply"), severity-tagged issues (e.g. "has
not been available for the past two days" → High), and natural openers/closers, so
that priority correlates with genuine severity language rather than being random noise.

Regenerate anytime with a new random seed / larger size by editing `per_category` in
`generate_dataset.py`.

## 5. AI / ML Explanation

- **Category classification**: TF-IDF (word + bigram frequencies weighted by inverse
  document frequency) turns each complaint into a numeric vector; a multinomial
  Logistic Regression model (`class_weight='balanced'`) then predicts one of 12 labels.
- **Priority prediction**: the same TF-IDF representation feeds a second Logistic
  Regression model trained to predict Low/Medium/High/Critical based on severity
  language (words like "fire", "hazard", "immediately", "collapse" push toward higher
  priority).
- **Sentiment analysis**: a third Logistic Regression model predicts
  Positive/Neutral/Negative tone.
- **AI Confidence Score**: the average of the three models' `predict_proba` confidence
  for their chosen label.
- **Duplicate detection**: cosine similarity between the new complaint's TF-IDF vector
  and every existing complaint's vector; the closest match is reported if it exceeds
  the 0.72 similarity threshold.
- Why Logistic Regression + TF-IDF and not a deep learning model? For a dataset of
  this size (a few hundred rows per class), classical ML with TF-IDF is fast to train,
  interpretable, doesn't need a GPU, and generalizes better than a deep network would
  on limited data — appropriate for a mini-project with real, explainable results.

## 7. Project Architecture

```
Browser (HTML/CSS/JS, Jinja2-rendered pages)
        │  fetch() calls with JWT bearer token
        ▼
FastAPI application (app/main.py)
   ├── Routers: auth_routes, complaint_routes, admin_routes
   ├── AI engine: app/ai/inference.py (loads .pkl models once, serves predictions)
   ├── Auth: JWT (python-jose) + bcrypt password hashing (passlib)
   └── ORM: SQLAlchemy models → SQLite (campus_helpdesk.db)
        │
        ▼
Trained models (model/*.pkl) produced by train_model.py from dataset/complaints.csv
```

## 14. Testing Instructions

1. Start the server (`uvicorn app.main:app --reload`).
2. Register a student account at `/register`.
3. Go to **Submit Complaint**, type something like:
   *"The Wi-Fi in the boys hostel has not worked for three days, I cannot submit assignments"*
   and click **Analyze with AI** — verify category/priority/sentiment/confidence appear.
4. Submit the complaint and note the ticket ID.
5. Log out, log in as `admin@campus.edu` / `Admin@123`, open **Admin Dashboard**.
6. Search/filter by category, priority, and status; open the ticket; change its status
   to **In Progress**, then **Resolved**; add a remark.
7. Log back in as the student, open **My Complaints**, view the ticket, and submit
   feedback (star rating + comment) — only available once the ticket is Resolved.
8. Visit **Admin → Analytics** to see charts and the AI model's Accuracy/Precision/
   Recall/F1/Confusion Matrix.
9. **Security checks:**
   - Try submitting a complaint containing `<script>alert('test')</script>` — it is
     escaped/sanitized and never executes.
   - Try a name/complaint containing an apostrophe like `O'Reilly` — stored and
     displayed correctly (SQLAlchemy parameterized queries prevent SQL injection).
   - Try submitting an empty complaint or a 5000-character complaint — both are
     rejected with a clear validation message, not a server crash.
   - Try fetching `/complaint/INVALID-TICKET-ID` — returns a friendly "not found"
     message instead of crashing.
   - As a student, try to open another student's ticket ID directly — returns
     `403 Forbidden`.

## 15. Advantages

- Removes manual, error-prone triage of incoming complaints.
- Consistent, explainable priority scoring based on real complaint language.
- Faster response to safety-critical issues via automatic priority escalation.
- Duplicate detection reduces redundant work for the admin team.
- Transparent AI confidence score builds trust in automated tags.
- Clean role-based separation between student and admin capabilities.

## 16. Limitations

- The dataset is synthetically generated; a production system should be retrained on
  real historical complaint data for higher real-world accuracy.
- Only English-language complaints are supported by the current TF-IDF vectorizer.
- Priority prediction accuracy (~74%) is lower than category accuracy — real deployments
  would benefit from a much larger, human-labeled dataset per priority level.
- Duplicate detection uses a fixed similarity threshold (0.72), which may need tuning
  as complaint volume grows.
- JWT tokens are stored in `localStorage`, which is acceptable for a mini-project but
  would need `httpOnly` cookies + CSRF protection for production hardening.

## 17. Future Scope

- Retrain on real, anonymized complaint history for improved accuracy.
- Add multilingual support (Hindi/regional languages) via multilingual embeddings.
- Add push/email notifications on status changes.
- Add a chatbot interface for guided complaint submission.
- Add role-based sub-departments (e.g. hostel wardens see only Hostel complaints).
- Replace Logistic Regression with fine-tuned transformer embeddings as the dataset grows.

## 18. Conclusion

This project demonstrates a complete, working pipeline from raw complaint text to an
automatically classified, prioritized, and tracked support ticket — combining NLP,
supervised machine learning, secure full-stack web development, and a real database,
in a way that mirrors how a production campus helpdesk system could be built and
scaled with more data.

## 19. 25 Simple Viva Questions & Answers

1. **What is the aim of this project?**
   To automate campus complaint classification, priority prediction, and tracking using AI/NLP.

2. **What AI technique is used for classification?**
   TF-IDF vectorization combined with Logistic Regression.

3. **Why TF-IDF instead of just word counts?**
   TF-IDF down-weights common words that appear in every document and up-weights
   words that are distinctive to a particular complaint, giving better features.

4. **What is Logistic Regression?**
   A supervised classification algorithm that estimates the probability of each class
   using a linear combination of input features passed through a sigmoid/softmax function.

5. **How many complaint categories does the system support?**
   12 — IT/Network, Infrastructure, Laboratory, Library, Hostel, Transport, Electricity,
   Cleanliness, Examination, Administration, Security, Other.

6. **How is priority predicted?**
   A separate Logistic Regression model, trained on the same TF-IDF features, predicts
   Low/Medium/High/Critical based on severity language in the complaint text.

7. **How does the system detect duplicate complaints?**
   By computing cosine similarity between the TF-IDF vector of the new complaint and
   every existing complaint; a similarity above 0.72 is flagged as a likely duplicate.

8. **What is cosine similarity?**
   A measure of the angle between two vectors; a value near 1 means the vectors (and
   hence the texts they represent) are very similar in meaning/wording.

9. **What is an AI confidence score in this system?**
   The average of the prediction probabilities from the category, priority, and
   sentiment models for their chosen labels.

10. **What database is used and why?**
    SQLite, via SQLAlchemy ORM — lightweight, file-based, requires no separate server,
    ideal for a mini-project, and easily swappable for PostgreSQL/MySQL later.

11. **How are passwords stored securely?**
    They are hashed using bcrypt (via passlib) before being stored; plain-text
    passwords are never saved or transmitted after login.

12. **How is user authentication handled?**
    JSON Web Tokens (JWT) — issued on login/register, sent as a Bearer token on every
    API request, and verified server-side on protected routes.

13. **How is SQL injection prevented?**
    SQLAlchemy's ORM uses parameterized queries internally, so user input is never
    concatenated directly into SQL strings.

14. **How is XSS (script injection) prevented?**
    Input is HTML-escaped server-side on save, `<script>` tags are stripped, and
    Jinja2 auto-escapes any dynamic content rendered into HTML templates.

15. **What does role-based access control mean here?**
    Students can only view/act on their own complaints; only admins can view all
    complaints, change status, assign departments, and see analytics.

16. **What metrics are used to evaluate the ML models?**
    Accuracy, Precision, Recall, F1-score, and the Confusion Matrix, computed on a
    held-out 20% test split.

17. **Why split precision, recall, and F1 instead of just accuracy?**
    Because complaint categories/priorities are imbalanced; accuracy alone can hide
    poor performance on minority classes, while precision/recall/F1 expose that.

18. **What is a confusion matrix?**
    A table showing how many predictions of each true class were classified into each
    predicted class, revealing exactly where the model gets confused.

19. **What Python libraries were used for the ML pipeline?**
    pandas, NumPy, and scikit-learn (TfidfVectorizer, LogisticRegression, train_test_split,
    metrics), plus joblib for saving/loading trained models.

20. **What web framework powers the backend, and why?**
    FastAPI — chosen for its speed, built-in request validation via Pydantic, automatic
    interactive API documentation, and native async support.

21. **What is a ticket ID and how is it generated?**
    A unique human-readable identifier (e.g. `TCK-2026-A1B2C3`) generated randomly and
    checked against the database for uniqueness before being assigned to a new complaint.

22. **Can a student see another student's complaint?**
    No — the backend checks `complaint.user_id == current_user.id` for students and
    returns `403 Forbidden` otherwise.

23. **How does the admin dashboard get its analytics?**
    Via `/api/admin/analytics`, which runs SQL `GROUP BY` aggregations on category,
    priority, status, and sentiment, plus average feedback rating, rendered as charts
    with Chart.js.

24. **What happens if a student submits an empty or extremely long complaint?**
    Pydantic validators reject it with a clear error message (minimum 5, maximum 3000
    characters) before it ever reaches the database or the AI models.

25. **How would you extend this project for production use?**
    Retrain on real complaint data, add multilingual NLP support, move JWT storage to
    httpOnly cookies, add email/push notifications, and migrate SQLite to PostgreSQL
    for concurrent multi-user scale.
